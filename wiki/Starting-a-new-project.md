# Starting a new project

Each experiment gets its **own GitHub repository**, generated by this tracker.
The generated repo pins the tracker to a git tag, so a reviewer years later
gets the exact version used to produce the data.

---

## The easy way: the generator window

```bash
cd ~/tracking
python3 new_project.py
```

or double-click **New Project.desktop** (Linux) / **New Project.command**
(macOS). See [Installation](Installation#making-the-generator-double-clickable)
for the one-time `chmod` that enables double-clicking.

The window asks for:

- **Project name** — letters, numbers, underscores; becomes the repo name
- **Location** — the parent folder the project is created inside (with a Browse button)
- **Open the project folder when done** — on by default

It shows the tracker version it will pin at the top. When the project is
created you get a green confirmation with the full path and the exact commands
for the next steps.

### If the tracker is not tagged

The window says so and disables the Create button, because a project pinned to
an untagged commit is not reproducible. It pre-fills the tag matching the
current version and offers a **Tag and push** button — one click creates the
tag and pushes it, then re-checks. You can also do it by hand:

```bash
cd ~/tracking
git tag v0.3.0          # must match `version` in pyproject.toml
git push origin v0.3.0
```

The same check rejects a **dirty working tree** (uncommitted changes mean the
tag does not describe the code that would actually run) and a **tag that
disagrees with `pyproject.toml`**.

## The command-line equivalent

```bash
cd ~/tracking
uv run tracker new-project --name pain_killers --path ~/projects
```

Identical scaffolding and identical checks — the window is just a front end.

---

## What gets created

```
~/projects/pain_killers/
    setup.py            ← the single file a reviewer downloads and runs
    pyproject.toml      ← analysis deps + tracker pinned to v0.3.0
    project.yaml        ← tracker configuration (read by app and notebook)
    1_pipeline.ipynb    ← preprocessing → tracking → postprocessing
    2_tracking/         ← tracker's working directory
        1_videos/       ← symlinks to raw videos (gitignored)
        2_pv/           ← TGrabs output (.pv files, background images)
        3_csv_individual/   ← TRex per-individual CSVs
        4_csv_video/    ← collated per-video CSVs
        masks/          ← include/ignore polygon CSVs
        tuning/         ← threshold sweep workspace
    3_analysis/         ← experiment-specific analysis
    README.md           ← reproduction instructions for reviewers
    .gitignore          ← excludes videos and large intermediates
```

## Publishing it

```bash
cd ~/projects/pain_killers
git init && git add -A && git commit -m "Initial scaffold"
gh repo create StefanMPopp/pain_killers --private --source=. --push
```

Do this early — the README in the project tells reviewers to fetch `setup.py`
from the repo, so those instructions only work once it exists.

---

## Adding videos

Videos are usually too large to commit, so they are **symlinked** into
`2_tracking/1_videos/` from wherever they actually live (external drive, NAS).
Two ways:

- In the tracker app: **🔗 Link video** in the top bar, paste the full path
- By hand:
  ```bash
  ln -s /Volumes/MyDrive/vid_001.MP4 ~/projects/pain_killers/2_tracking/1_videos/vid_001.MP4
  ```

Dedicated short clips for parameter tuning go in `2_tracking/tuning/1_videos/`
instead, and are used in the app's Tuning mode.

## First run

```bash
cd ~/projects/pain_killers
uv sync --extra tracking
uv run jupyter lab 1_pipeline.ipynb
```

Set `meta_real_width`, `track_max_individuals` and `individual_prefix` — either
in `project.yaml` directly or in the app's **Parameters** tab. See
[Using the tracker](Using-the-tracker).
